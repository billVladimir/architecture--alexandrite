# Задание 2

## Анализ системы в контексте мониторинга

Текущая ситуация:

- Сайт подключён к Яндекс Метрике, она фиксирует поведение пользователей в онлайн-магазине.
- После открытия API появились B2B-заказы через интеграции, которые Метрика не отслеживает.
- Нагрузка растёт и задержки в заказах увеличиваются.
- Жалобы пользователей являются индикатором нестабильной работы системы.
- На текущий момент нет централизованного мониторинга надежности, доступности и ошибок системы.

## Мотивация

Обоснование для бизнеса:

- Снижение количества просроченных заказов. Мониторинг позволит вовремя обнаруживать задержки и сбои в цепочке обработки заказов.
- Сокращение потерь клиентов. Быстрая реакция на аномалии = меньше недовольных заказчиков = выше LTV.
- Прозрачность. Команда сможет принимать решения на основе данных, а не догадок.
- Профилактика инцидентов. Мониторинг позволит предотвратить отказ систем до того, как это почувствуют пользователи.

## Выбор подхода к мониторингу

Веб-приложения и API -> RED
Очереди / RabbitMQ -> USE
Инфраструктура (CPU, память, БД) -> Четыре золотых сигнала

## Метрики

### Веб-приложения и API

**Модули: Онлайн-магазин, CRM, MES**

1. RPS (Number of requests). Понимание нагрузки и аномалий в трафике.
2. HTTP 500 / Errors. Индикатор деградации.
3. Response time (latency). Пользовательский опыт зависит от отклика.

### RabbitMQ (USE-подход)

**Канал обмена заказами с MES**

1. Number of messages in flight. Отслеживание текущей загруженности очереди.
2. Dead-letter-exchange messages. Выявление неправильной обработки сообщений.

### Инфраструктура (4 золотых сигнала)

1. CPU % / Memory Utilisation (на API и БД). Чтобы понимать, не происходит ли деградация под нагрузкой.
2. Number of DB connections. Переполнение пула соединений = тормоза в системе.
3. Размеры баз данных (Size of shop/MES db). Рост объёма может сигнализировать о проблемах с архивированием или очисткой.
4. Number of simultanious sessions. Отражает пиковые нагрузки в реальном времени.
5. Traffic (KB sent/received). Всплески могут указывать на DDoS, некорректные интеграции, утечки.

### Дополнительные метрики

1. Время прохождения заказа от статуса SUBMITTED до SHIPPED. Отслеживание SLA выполнения заказов.
2. Количество заказов по статусам (MES). Диагностика “застревания” заказов на определённой стадии.
3. Ошибки интеграции MES/CRM через очередь. Быстро видеть, когда что-то пошло не так в цепочке.

## План действий

Внедрить мониторинг для отслеживания технического состояния систем «Александрит», включая API, очередь сообщений и инфраструктуру, с целью раннего выявления проблем, устранения «узких мест» и повышения стабильности бизнес-процессов.

1. Выбор и развёртывание системы мониторинга

   2. Создать инстанс time-series базы (Prometheus). Запуск в Yandex Cloud.
   3. Развернуть Grafana для визуализации.
2. Интеграция с микросервисами и API
3. Мониторинг очередей (RabbitMQ)
4. Мониторинг баз данных и системных ресурсов
5. Создание дашбордов
